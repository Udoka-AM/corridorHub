## Not built, on purpose or not yet

| | Why it is not there | What would change it |
|---|---|---|
| **A signed anchor** | Nobody has signed one | A design partner or an anchor agreeing to a testnet integration. Everything below is downstream of this |
| **SEP-6 collections** | No signed anchor has exercised the flow, so it would be a guess | The first collecting anchor, then the deposit flow behind `openCollection` |
| **`stellar.pathPayment`** | The planner produces the edge; the leg is unwritten | Writing it, so a balance in EURC or MGUSD can fund a payout |
| **MGUSD, PYUSD, USDT issuers** | Unset until each is verified against the issuer's own `stellar.toml` | Verification, or a deployment supplying its own with `CORRIDOR_STELLAR_ISSUER_…` |
| **A treasury console** | The prototype's read Tempo and was removed rather than left misreporting | The engines already produce the data; it is a user interface |
| **A mainnet run** | No anchor, no customer, nothing to run | A signed anchor and a design partner |
| **Ramp's wallet providers and cross-chain deposits** | Out of MVP by decision: an app brings its own signer through `signXdr`, and Ramp sponsors the reserve, trustline and fee. Passkey login and Soroban smart accounts are a milestone after MVP — on Stellar they are two separate builds, and a wallet provider supplies neither the sponsorship nor a contract account ([ADR 0013](/decisions/0013-ramp-and-hub-share-one-core#declared-and-not-built)). SEP-6/24 collections are declared and not built; x402 and the MCP server are built | A first app on the sandbox, and the first collecting anchor |
| **The Tron USDT lane** | Blocked upstream, not by us. NEAR Intents lists Stellar USDC as a token but does not route it: checked 23 Oct 2026, `Tron USDT → Stellar USDC` and `Solana USDC → Stellar USDC` both answer *"Quoting for this pair is not available"*, and Stellar as an origin fails in both deposit modes. `Tron USDT → Solana USDC` quotes fine, at about 0.14% on $150, and there is a $100 minimum swap | The CCTP burn on Solana is now built, so the two-hop path exists: Tron → Solana by intent, Solana → Stellar by burn-and-mint. What is left is the $100 minimum, and a first real run |
| **The confidential lane** | Deferred to Stellar confidential tokens rather than bolted on elsewhere ([ADR 0005](/decisions/0005-confidential-lane-deferred)) | Confidential tokens with auditor keys on Stellar |

## Next, in order

<Steps>
  <Step title="A signed anchor on testnet">
    `SepAnchor` against a real anchor's `stellar.toml` instead of a stub: the SEP-10 handshake, a SEP-38 quote and a SEP-31 order that an anchor actually fills. This is the one step everything else waits on.
  </Step>
  <Step title="A first corridor end to end">
    EUR → KES: a payout funded from a USDC balance on Stellar and paid out in shillings by a licensed anchor, reconciled from the funding payment to the bank credit.
  </Step>
  <Step title="Design-partner pilots, read-only first">
    Sixty days watching the Stellar accounts a licensed payout company already runs, matched against its own payout records. Then routing, on the company's own signer.
  </Step>
  <Step title="Collections">
    SEP-6 deposits behind `openCollection`, which makes the importer flow real rather than half-real.
  </Step>
  <Step title="More spokes">
    XOF and TZS next, then Ghana and South Africa; a licensed naira anchor whenever one exists, which moves NGN onto the hub and makes `cctp.transfer` unnecessary for it.
  </Step>
  <Step title="A console">
    The data already exists in the ledger, the saga tables and the matcher. What is missing is the interface over it.
  </Step>
</Steps>

## Production hardening

| Area | Today | Production |
|---|---|---|
| Ledger | PGlite (embedded Postgres) | Managed Postgres, same schema and triggers |
| Custody | Signer interface on every vault; AWS KMS and Turnkey adapters | The customer's KMS or MPC for every vault |
| Horizon | The public instance | `CORRIDOR_HORIZON_URL` at a private instance; observers already resume from a stored cursor |
| Issuers | USDC and EURC set; three deliberately unset | Each verified against its `stellar.toml`, or supplied per deployment |
| Stablecoins | USDC funds payouts; the others are booked and reconciled | The path-payment leg, so EURC and MGUSD balances can fund payouts directly |
| Compliance | The reconciliation trail as audit evidence | Address screening and a Travel Rule hook before a payout is funded; scheduled audit exports |
| Fees | XLM float per vault, booked from the chain | The same, with alerting on float |

## Known limitations

<AccordionGroup>
  <Accordion title="Testnet runs move XLM, not USDC">
    A funded testnet USDC trustline needs an issuer faucet. `transferWithReference` is the same call with a different asset, and the asset registry and `trustAsset` are built, but no testnet run has moved USDC itself.
  </Accordion>
  <Accordion title="The anchor assigns the funding memo">
    On a SEP-31 leg the Corridor Reference cannot ride in `MEMO_HASH`, because the anchor's own memo must. The reference moves to the SEP-31 fields and the join key becomes the anchor's transaction id, which funding already records — but it is one join key rather than one everywhere.
  </Accordion>
  <Accordion title="Base has no memo">
    In read-only mode, Base movements match by amount and counterparty rather than by reference. That is weaker, and the pilot's own output shows it.
  </Accordion>
  <Accordion title="Precision at a 6 dp spoke">
    A payout whose amount carries a seventh decimal cannot be paid on Solana or Base and fails at the edge rather than silently losing a stroop. That is the intended behaviour, and it is still a corridor a customer cannot use for that amount.
  </Accordion>
</AccordionGroup>
