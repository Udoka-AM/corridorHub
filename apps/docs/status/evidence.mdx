Every claim in this documentation can be checked. This page lists what has actually run, with the transaction behind it and the command that reproduces it.

<Warning>
**Nothing has run on Stellar mainnet, and no anchor is signed**, so no real local currency has moved on Stellar. The runs below are on Stellar testnet with a mock anchor. The one run against real money is the prototype's, on Tempo, and it is labelled as such.
</Warning>

## Stellar testnet

Both runs on **17 October 2026**, on Stellar testnet, signed through the signer interface.

### The reference survives a real transaction

`pnpm stellar:smoke` sends a payment with a Corridor Reference as its `MEMO_HASH`, then asks Horizon for that account's payments and finds the movement again by its memo — the join reconciliation uses, with no indexer in the path.

```text
reference 0x020114290001a1494e71ec7073bfffc84d758d67d2c6cf255f57adc6fd6cb505
sent 0.1 XLM   → stellar.expert/explorer/testnet/tx/175ad420…54781c
read back 0.1 XLM with the same reference, decoded out of MEMO_HASH
ledger 5241532 · 2026-10-17T10:00:47Z
```

| What | Result | Transaction |
|---|---|---|
| Payment carrying the reference in `MEMO_HASH`, read back off Horizon and decoded whole | Reference matched byte for byte; checksum valid | [175ad420…](https://stellar.expert/explorer/testnet/tx/175ad4206f85b279831178a5ad896da123105005f265fb5c798ae3d09254781c) |

The reference decodes to version 2, kind payout, **EUR → KES**, public lane, payout id `01a1494e-71ec-7073-bfff-c84d758d67d2`, and a valid checksum. See [Corridor Reference](/architecture/corridor-reference#a-real-one-decoded).

```bash
pnpm stellar:wallets && pnpm stellar:smoke
```

### A whole payout through the saga engine

`pnpm stellar:payout` plans a EUR → KES route, reserves the customer's balance, opens an anchor order, funds it exactly once with a real Stellar payment, books every movement double-entry, and prints the ledger invariants.

| What | Result | Transaction |
|---|---|---|
| Route planned, balance reserved, order opened and funded exactly once, every movement booked | Saga `completed`; `checkInvariants()` clean; customer balance closed to zero | [ac025984…](https://stellar.expert/explorer/testnet/tx/ac025984a302d98edbb771bcf7f39f21fa83134938e10510e76d71ccba33bf89) |

```bash
pnpm stellar:payout
```

The funding payment carries **the anchor's own memo**, not the Corridor Reference — `memo_type: text`, `memo: mock-8313e798`, as Horizon reports it. That is the real SEP-31 shape: a receiving anchor assigns the memo, so the reference travels in the SEP-31 fields and the join key becomes `(anchor, transaction id)` ([ADR 0003](/decisions/0003-reference-in-memo-hash)). An [earlier run](https://stellar.expert/explorer/testnet/tx/88074bfac3cead1adeb75209cd9aa685bfda44589397b6990dbc92deccbdc10e) took the simpler path with the reference in `MEMO_HASH`; both paths are exercised.

<Note>
Both runs move **XLM**, because a funded testnet USDC trustline needs an issuer faucet. The USDC path is the same call with a different asset. The anchor in the payout run is `MockPartner` with `chains: ["STELLAR"]`: the route, the saga, the Stellar payment and every ledger entry are the real ones, and only the fiat side is simulated.
</Note>

### Against a real SEP server

The hardest thing to show without a signed anchor is that the SEP path works against something Corridor does not control. `examples/anchor` brings up **Stellar's own Anchor Platform**, configured as a receiving SEP-31 anchor, and the same `pnpm stellar:payout` runs against it over the network.

```bash
./examples/anchor/up.sh
CORRIDOR_ANCHOR_BASE_URL=http://localhost:8080 \
CORRIDOR_ANCHOR_PLATFORM_URL=http://localhost:8085/ \
CORRIDOR_PAYOUT_CURRENCY=USD pnpm stellar:payout
```

| Step | Result |
|---|---|
| SEP-1 | `stellar.toml` discovered over HTTP at a base URL that is not the home domain |
| SEP-10 | The anchor's challenge **verified before the vault signed it**, and exchanged for a JWT |
| SEP-38 | A firm quote: 7 `stellar:native` sold for `iso4217:USD` |
| SEP-31 | Order opened with the quote, the beneficiary fields and the Corridor Reference; the anchor returned its receiving account and memo `13453` |
| Funding | A real Stellar payment carrying **the anchor's `id` memo** — [`ecc31ac7…`](https://stellar.expert/explorer/testnet/tx/ecc31ac72a77ff5afbb211db2f41a2e96acf83200b484ff6bf87671337666c6e) |
| The anchor's observer | The anchor saw the payment on-chain by itself and advanced the transaction |
| Polling | SEP-31 has no webhook, so the saga polled `GET /transactions/{id}` to `completed` |
| The books | `paid 1538 USD at 2.1978`; invariants clean; the customer's balance closed to zero |

<Note>
No local currency moved: the anchor is Stellar's reference implementation, run locally, and telling it the beneficiary was paid is a step a real anchor performs itself off its own rail. Everything on Corridor's side of the exchange is real, and nothing in the adapter is stubbed. See [`examples/anchor`](https://github.com/Udoka-AM/corridorHub/tree/main/examples/anchor).
</Note>

### Ramp, through the SDK

On **19 October 2026**, `pnpm ramp:demo` ran the hosted API in-process against Stellar testnet and drove it only through `@corridor/ramp-sdk`: a sandbox app signed up, an end user was onboarded with reserves sponsored, and a payout ran to `completed` against the mock anchor. The user's key stayed in the script, which signed through the SDK's `signXdr` hook. It settled in XLM because testnet has no USDC faucet.

## Read-only reconciliation

`pnpm watch:report` runs the same observers and matcher against Stellar accounts Corridor does not control, with no keys loaded:

```bash
CORRIDOR_WATCH=GABC…,GDEF… pnpm watch:report
```

It is covered by five tests in `packages/recon/src/readonly.test.ts` — reference matching, heuristic matching, short, missing and unexpected — and has not been run against a design partner's production accounts, because there is no design partner yet.

## The prototype, on Tempo

Corridor's earlier prototype settled on **Tempo** and reached its payout rails through bespoke provider APIs. It is a different repository and a different build; its result is kept here because it is where the saga engine, the ledger and the reconciliation matcher were proven against real money.

On **11 October 2026**, the prototype moved real money end to end: **2.90 USDC.e on Tempo became ₦3,891.48 in a Nigerian bank account in 74 seconds**. It went Tempo to Base and Base to Solana through Across, then Paj paid out in naira. The payout was funded by the founder and paid into the founder's own account.

## What is not evidenced

Stated here so nothing has to be inferred from an absence.

- **No signed anchor**, so no real local currency has moved on Stellar. The SEP path has run against Stellar's own Anchor Platform locally, not against a licensed anchor.
- **No mainnet run.** Code paths are identical; nothing has run on Stellar mainnet.
- **No SEP-6 collection**, anywhere.
- **No `cctp.transfer`**, so no Stellar → Solana movement has happened.
- **No `stellar.pathPayment`**, so no on-ledger FX has run.
- **No treasury console**, for Stellar.

See [Roadmap](/status/roadmap) for what would change each of those.
