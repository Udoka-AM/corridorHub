Balanced books are not the same as correct books. A ledger can balance perfectly while missing a movement the chain recorded. Corridor reconciles in both directions: **is everything the chain saw booked?** and **does each vault hold what the books say?**

## Observers

| Venue | Observer | Observation `externalRef` |
|---|---|---|
| Stellar | `StellarObserver`: Horizon payments in and out of the watched accounts, with the memo joined in. With `unreferenced` it also reports account funding, sponsored reserves, plain inbound payments, and the XLM fee each outbound transaction charged | `${txHash}:${operationId}`, and `${txHash}:fee` for the fee |
| Anchors | SEP-31 status, polled; signed webhooks where a provider has them, stored once per order status | `${partner}:${orderId}` |
| Solana | Stablecoin balance changes of any address, with the memo reference when present | signature, or `${signature}:${asset}` when one transaction moved several stablecoins |
| Base | USDC and EURC `Transfer` logs in and out of any address | `${txHash}:${logIndex}` |

The Stellar observer resumes from a **stored Horizon paging token**, so restarts neither miss nor double-count payments.

<Note>
Horizon's payment endpoint has to be called with `join=transactions` for the memo to arrive in the same call, and the SDK turns every `_links` entry into a method, so the joined transaction arrives as `transaction_attr` and its ledger sequence as `ledger_attr`. `normalizeRecord` lifts both out, and cross-checks the ledger sequence against the operation's TOID (`paging_token >> 32`). Getting this wrong silently loses every memo, so it is covered by tests.
</Note>

In a [read-only pilot](/flows/read-only-pilot) the same observers watch the customer's own Stellar accounts and `reconcileReadOnly` matches them against the customer's own payout records instead of Corridor's ledger.

## Matching

```ts
const results = await reconcile(ledger, observations);
summarize(results); // { matched, amount_mismatch, unbooked, unreferenced }
```

| Status | Meaning | Action |
|---|---|---|
| `matched` | Booked, same amount | None |
| `amount_mismatch` | Booked, but the ledger amount differs from the chain | Investigate: wrong amount booked, or a partial delivery |
| `unbooked` | Carries a Corridor Reference but nothing was booked | Our own movement went unrecorded |
| `unreferenced` | No reference and not booked | An unidentified deposit: never credited automatically |

The comparison uses `entryTotal(..., { excludeLiabilities: true })`. Now that the hub and its spokes settle in the same asset, a payout debits the customer's hold in USDC *and* moves USDC on the chain, and only the second is what an observer saw.

## Vault accounting from the chain

Memo-tagged movements are booked by the legs that make them. Two kinds of movement are not, and Corridor books them from the chain:

<CardGroup cols={2}>
  <Card title="Fees" icon="fuel">
    Stellar charges each transaction's fee in **XLM** to its source account. Every fee a vault paid is observed with the transaction that paid it and booked to `expense:gas`, keyed by that transaction.
  </Card>
  <Card title="Funding" icon="banknote">
    Deposits into a vault from an **approved funding source** — owner wallets on mainnet, Friendbot on testnet — are booked to `equity:owner`.
  </Card>
</CardGroup>

Movements are processed in chain order, so a top-up is booked before the fees it pays for. Anything else without a reference stays `unreferenced`: a payment sent without a memo may be a customer's money, so it is never credited automatically. See [ADR 0008](/decisions/0008-book-from-the-chain).

## The vault check

```ts
const checks = await checkVaults(accounts, ledger, [
  { name: "treasury", address, asset: "USDC", venue: "stellar", onchain },
]);
// { vault: "treasury", onchain, ledger, diff, status: "balanced" | "drift" }
```

The difference is exact, not approximate, because the ledger keeps Stellar's own 7 decimal places ([ADR 0012](/decisions/0012-seven-decimal-ledger)). A tolerance would be a hole in exactly the check that is meant to catch drift.

Alongside it, `checkInvariants()` re-verifies globally that every entry balances per asset and that the balance projection equals a full recompute from the postings. `pnpm stellar:payout` prints it at the end of every run.

## What this gives an auditor

Every booked movement names the transaction that caused it, the journal is append-only, and the reference ties a bank credit, an anchor order and a Stellar payment to the same payout. A reviewer can take any reference from the ledger, look it up on an explorer, and see the same amount.
