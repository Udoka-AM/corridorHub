Across moves value between the hub and the spokes. Corridor uses its **Swap API**, which returns ready-to-sign calldata, and tracks each deposit until a relayer fills it on the destination chain.

<Info>
**Live on mainnet.** On 11 Oct 2026 the Across adapter bridged Tempo → Base → Solana for a live naira payout ([Evidence](/status/evidence#live-on-mainnet)). The `across.bridge` saga leg wraps it: it takes pathUSD or USDC.e on Tempo, records each deposit before waiting on its fill, and books the amount that arrived, Across's fee and the origin gas from the chains. Testnet flows use `bridge.simulated`, which has the same interface.
</Info>

## Route shape

Across has no direct Tempo ↔ Solana route, so the hub reaches Solana in **two hops through Base**. Each hop is its own saga leg, and between hops the funds sit in the customer's own relay address on Base. A failure after a deposit stops the payout for a person rather than guessing, because the value has already crossed chains.

Paj, the naira partner, settles on Solana, so a naira payout uses **both** hops. A partner that settles on Base would be paid after one. Live quotes verified on 29 September 2026: Tempo USDC.e → Base USDC, 5 USDC in, fill ~1 s, fee ≈ $0.004; Base USDC → Solana USDC, fill ~8 s, fee ≈ $0.0006.

## API

| Environment | Base URL |
|---|---|
| Mainnet | `https://app.across.to/api` |
| Testnet | `https://testnet.across.to/api` |

<Steps>
  <Step title="Quote">
    `GET /swap/approval` with origin and destination chain ids, input and output tokens, amount in base units, depositor and recipient. Returns approval transactions, the deposit transaction, the expected output and an expiry.
    ```ts
    const q = await quote({
      env: "mainnet",
      originChainId: CHAINS.tempo, destinationChainId: CHAINS.base,
      inputToken: TOKENS.tempoPathUSD, outputToken: TOKENS.baseUSDC,
      amount: 5_000_000n, depositor: vault, recipient: relay,
    });
    ```
  </Step>
  <Step title="Execute">
    `executeEvm(sender, q)` sends any approvals, then the deposit, and returns the deposit transaction hash.
  </Step>
  <Step title="Track the fill">
    `GET /deposit/status` until the status is `filled` (with `fillTxnRef`), or `expired` / `refunded`. `waitForFill` polls with a deadline.
  </Step>
</Steps>

<Note>
CCTP-backed routes return `quoteExpiryTimestamp: 0`. The adapter treats zero as "no expiry" rather than "already expired".
</Note>

## Compensation design

Each hop is its own leg, so if the second hop fails after the first has filled, the saga compensates the first by bridging back from Base to the hub. Because each hop books separately, the ledger always shows where the money is: on Tempo, on Base, or in flight with a deposit hash.

## Testnet findings

Across has no Tempo testnet deployment, so Moderato runs use `bridge.simulated`, which has the same interface: the Tempo side is real (pathUSD moves to an escrow with the reference as memo) and the far side is simulated. A live Across testnet deposit from Base Sepolia to Solana devnet ([0x782d8b52…](https://sepolia.basescan.org/tx/0x782d8b52d1278892e5215a7a72bf731fa0e205a9274f38f99e0bcb9992c76e02)) burned the USDC and completed Circle's CCTP v2 attestation, but the final Solana mint is restricted to Across's designated `destinationCaller` (its testnet relayer), which did not execute it. The mainnet run uses the same adapter. See [ADR 0007](/decisions/0007-live-bridge-first).
