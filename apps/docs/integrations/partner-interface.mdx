A spoke is whatever pays local currency. Most of them are Stellar anchors, reached over [the SEPs](/integrations/sep-anchors); one of them, for now, is a licensed partner that settles on Solana. Both implement this interface, so the legs, the webhooks and reconciliation never depend on which.

## The interface

```ts
type PartnerChain = "STELLAR" | "SOLANA" | "BASE";

interface RampPartner {
  readonly id: string;
  readonly payoutCurrencies: readonly Fiat[];
  readonly collectionCurrencies: readonly Fiat[];
  readonly chains: readonly PartnerChain[];

  rates(currency: Fiat): Promise<Rates>;
  openPayout(req: PayoutRequest): Promise<PartnerOrder>;          // offramp
  openCollection(req: CollectionRequest): Promise<PartnerOrder>;  // onramp
  getOrder(id: string): Promise<PartnerOrder>;

  verifyWebhook(rawBody: string, headers: Record<string, string | undefined>, now?: Date): boolean;
  parseWebhook(rawBody: string): PartnerOrder;
}
```

`SepAnchor` implements it over SEP-1/10/12/38/31 and declares `chains: ["STELLAR"]`. `PajPartner` implements it over a REST API and declares `["SOLANA"]`. `MockPartner` implements it for tests and testnet runs, on whichever chain it is given.

## The order

Every provider is normalised to one lifecycle: `open → processing → completed | failed`.

<Note>
`fundingMemo` is the honest part of the interface. A SEP-31 anchor assigns the memo for the funding payment, so Corridor's own reference cannot ride in `MEMO_HASH` on that leg. The funding code uses `fundingMemo` when it is set and the reference otherwise, and the join key becomes `(anchor, transaction id)` — which the saga already records to make funding exactly-once.
</Note>

## What Corridor needs from a spoke

<Steps>
  <Step title="Settle in a stablecoin on a chain Corridor reaches">
    Stellar for an anchor. A provider that settles elsewhere needs a cross-chain hop, and today only the naira corridor has one.
  </Step>
  <Step title="One-off addresses or memos">
    A fresh funding address or memo per payout, and a fresh virtual account per collection, so every movement maps to exactly one order.
  </Step>
  <Step title="Echo the reference">
    Carry the 32-byte Corridor Reference in a field you return, and into the bank narration where you can. A statement line should trace back to the payout that caused it.
  </Step>
  <Step title="A status Corridor can poll or receive">
    Either a polled endpoint (what SEP-31 gives) or HMAC-signed webhooks over a timestamp and the raw body, verified in constant time within a five-minute window.
  </Step>
</Steps>

## How Corridor uses it

- A `PartnerRegistry` picks the provider per (currency, direction, chain).
- **Exactly-once funding:** the payout leg records the order and the funding transaction durably, so retries reuse them rather than paying twice.
- **Failure after funding** stops at `manual_review`; Corridor never unwinds its own books while the money is at the provider.
- **Anchor rounding** is booked as dust held for the customer, not written off.
- Each completed order becomes an `Observation` (`partner_fiat`, `${partner}:${orderId}`) for [reconciliation](/architecture/reconciliation).
